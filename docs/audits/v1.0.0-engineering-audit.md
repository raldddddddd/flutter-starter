## Verdict

**Yes, there are blocking technical issues.** There are three, and each has a small, local fix:

1. **C1**: a logout that overlaps a failed rotated-refresh-token write brings the logged-out session back, and the epoch guard then accepts writes for the old account.
2. **C2**: a logout during `establishSession` leaves the app authenticated in memory with no stored envelope.
3. **C3**: Android release builds (every flavor) do not declare `INTERNET`, so they cannot reach the API.

The rest of the architecture matches the spec well. Because `v1.0.0` is already pushed, I recommend fixing C1–C3 (ideally with I1–I4 too) and tagging `v1.0.1`, rather than moving the existing tag.

## 1. Critical issues

### C1. A failed rotated-token write during logout brings the session back
**Where:** `lib/core/session/session_manager.dart:182-191`

```dart
if (refreshToken != null && refreshToken != _refreshToken) {
  try {
    await _writeEnvelope(accountId, refreshToken);
  } catch (error, stackTrace) {
    _accessToken = null;
    _setState(SessionStatus.authenticatedOffline, accountId: accountId); // no epoch check
    return StorageFailure(cause: error, stackTrace: stackTrace);
  }
  _refreshToken = refreshToken;                                          // also before the epoch check
}
if (_snapshot.epoch != epoch || _snapshot.accountId != accountId) { ... }
```

**Why it matters:** Suppose `logout()` runs while the envelope write is in progress and the write then fails. The catch block publishes `authenticatedOffline` for the logged-out account at the **new** epoch. The gate sends the user back into the app as the old account. `isCurrentSession(oldAccount, newEpoch)` also returns `true`, so any repository operation that starts after this point passes the epoch guard and commits the old user's data. That breaks the spec's central guarantee (§15, §19, §79 "logout cannot allow an old request to restore previous-user data"). On the success path, `_refreshToken` is also assigned before the epoch re-check, which leaves a live refresh token in memory after logout.

**Probe output:** `after logout-during-rotation-failure: result=StorageFailure status=authenticatedOffline account=alice current=true`

**Smallest fix:** After the `await`, and before any state or field mutation (in both the `catch` block and the success path), return `AuthenticationFailure` when `_snapshot.epoch != epoch || _snapshot.accountId != accountId`. Add a regression test that gates the secure write, calls `logout()`, then fails the write.

### C2. A logout during `establishSession` leaves a live in-memory session
**Where:** `lib/core/session/session_manager.dart:81-103`

The method advances the epoch and awaits `_writeEnvelope(...)`. It then sets `_accessToken`, `_refreshToken` and `authenticatedOnline` without checking that the epoch is still the one it created.

**Why it matters:** If the user logs out while the envelope write is pending, `logout()` sets `unauthenticated` and queues the envelope delete. Then `establishSession` resumes and sets `authenticatedOnline` with live tokens. The user stays signed in even though they logged out, and the next cold start silently signs them out because the envelope is gone. This is the documented entry point for the future login adapter (`// Used by a future login adapter`), so every product built from the starter inherits the bug. In v1 the only caller is the dev sample-demo button, which is why I list it second.

**Probe output:** `after logout-during-login: status=authenticatedOnline account=alice access=a envelope={}`

**Smallest fix:** Capture `final epoch = _snapshot.epoch;` right after `_advanceEpoch()`. After the write (and in its `catch`), return without touching state if `_snapshot.epoch != epoch`. Add a test that runs a gated write, then logout, then releases the write.

### C3. Android release builds cannot access the network
**Where:** `android/app/src/main/AndroidManifest.xml`. `android.permission.INTERNET` is declared only in `src/debug/` and `src/profile/`.

**Why it matters:** `flutter build appbundle --release --flavor prod` (the command in `docs/release.md`) produces an app with no network permission. Every request, including token refresh, fails as a connection error. Restoration therefore always lands in `authenticatedOffline`, and the app can never reach `authenticatedOnline`. CI does not catch this because it builds only `--debug`.

**Smallest fix:** Add `<uses-permission android:name="android.permission.INTERNET"/>` to the main manifest. Optionally add a CI step that checks it, for example `flutter build apk --release --flavor prod --dart-define-from-file=config/prod.json`. The release build is debug-signed, so no secrets are needed.

## 2. Important issues

### I1. Account-scoped `user.*` preferences leak to the next account when secure material is lost
**Where:** `lib/core/session/session_manager.dart:116-128` (missing or corrupt envelope → `unauthenticated` with no cleanup) and `:81-103` (`establishSession` never clears the previous identity's scope).

**Why it matters:** Secure storage is explicitly losable (§21). Android keystore resets and keychain loss both happen in practice. When the envelope disappears, the previous user's `user.*` preferences stay behind. They are not keyed by account, so the next account that signs in reads them. The same leak happens when `establishSession` switches identity without a logout in between. The Drift rows are account-keyed, so they don't leak, but they also never get wiped.

**Probe output:** `bob sees user.lastFilter=alice-private`

**Smallest fix:** When `restore` reads a *definitively* missing or corrupt envelope (not a read exception, which may be transient), call `_preferences.clearUser()`. In `establishSession`, when the new `accountId` differs from the last known one, clear `user.*`. Optionally add a `clearAllAccountData()` that wipes user-scoped tables when the old account is unknown.

### I2. The flavor/`APP_ENV` mismatch check runs only in debug, and `APP_ENV` defaults to `dev`
**Where:** `lib/app/app_config.dart:15-27` (`assert(...)` plus `defaultValue: 'dev'`)

**Why it matters:** A release `--flavor prod` build made without `--dart-define-from-file`, or with the wrong JSON, silently runs as `dev`. It then uses the fake sample API, enables the dev "Open sample demo" local session on `/login` (`app_router.dart:88`), and turns on non-prod network logging, all under the production application ID. `assert` is stripped in release builds, so nothing stops this (spec §50/§52 flavor isolation).

**Smallest fix:** Replace the `assert` with a real check: `if (appFlavor != null && appFlavor != environment.name) throw StateError(...)`. Optionally make a missing `APP_ENV` in release (`kReleaseMode`) an error too.

### I3. `main()` crashes before `runApp` if the fresh-install cleanup throws
**Where:** `lib/main.dart:11-14`. `FreshInstallPolicy.ensureInitialized()` is awaited unguarded, and `installErrorHooks` is only installed later, inside `bootstrap()`. `test/persistence/fresh_install_policy_test.dart:42` confirms that the policy rethrows.

**Why it matters:** A keystore or keychain failure during `deleteAll()` on first launch leaves a blank app with an unlogged error. §21 says "the application must not crash" on secure-storage problems.

**Smallest fix:** Call `installErrorHooks` first. Then wrap the policy in `try/catch`, log the error, and continue to `runApp`. Leaving the marker unset means the cleanup retries on the next launch.

### I4. Unexpected errors caught by repositories never reach logging
**Where:** `lib/features/sample/data/sample_repository.dart:107-108` and `:152-155` (catch everything → `mapNetworkError` → `UnknownFailure`), `lib/core/logging/app_provider_observer.dart:19` (skips every `AppFailure`, including `UnknownFailure`), and the action notifiers, which store `AsyncError` as ordinary `Notifier` state, so `providerDidFail` never fires.

**Why it matters:** A `TypeError` from a malformed DTO in `DioSampleApiService.fromJson`, or a programming bug in the transaction, is shown to the user as "Something went wrong" and logged nowhere. §7 and §63 require unexpected errors to stay observable.

**Smallest fix:** When `mapNetworkError` produces an `UnknownFailure`, log it with its cause and stack. For example, give the repository an `AppLogger` and log in the `catch` when the result is `UnknownFailure`. Also narrow the observer's skip from `AppFailure` to "`AppFailure` other than `UnknownFailure`".

### I5. Developer error output is suppressed
**Where:** `lib/core/logging/error_hooks.dart:6-12` and `lib/core/logging/app_logger.dart:31-42`

`FlutterError.onError` is replaced without calling `FlutterError.presentError`, so debug builds lose the standard framework error dump (overflow, build and assertion details). `DeveloperLogger.error` also never passes `error:` to `developer.log`, so the exception itself is dropped in every build and only the message and stack are logged.

**Why it matters:** Development observability is worse than an unmodified Flutter app. The redaction concern in the comment is reasonable for release builds, not for debug.

**Smallest fix:** In `installErrorHooks`, call `FlutterError.presentError(details)` when `kDebugMode`. In `DeveloperLogger.error`, pass `error: error` when `kDebugMode`.

### I6. There is no connectivity or resume trigger to leave `authenticatedOffline`
**Where:** `lib/core/session/session_providers.dart:12-15`. `sessionRestorationProvider` is `keepAlive` and calls `restore()` once. Nothing else in `lib/` calls `restore()` (checked with grep).

**Why it matters:** §14 says "connectivity recovery should trigger another restoration/refresh attempt." Today recovery happens only as a side effect: an authenticated request gets a 401 (it was sent without a token) and the interceptor refreshes. With the dev fake API, which never sends HTTP, an offline session stays offline until the app restarts. `docs/session_network.md` says "a later call to `restore` retries", but nothing in the app makes that call.

**Smallest fix:** Add an `AppLifecycleListener` (in `AppRoot`, or in a small keep-alive provider) that calls `sessionManager.restore(refresher)` on `resumed` while the status is `authenticatedOffline`. This needs no connectivity package. Alternatively, document the 401-driven recovery as the v1 decision in `docs/spec.md`, as the spec's change rule (§80) requires.

## 4. Already implemented correctly

- **SDK and dependency reproducibility (§3, §49):** Flutter 3.47.5 pinned in `.fvmrc` and used by CI (`flutter-version-file`). `pubspec.lock` is committed and CI uses `--enforce-lockfile`. Regenerated code produced no diff.
- **Riverpod 3 (§4–§6, §33–§34):** Only generated `@riverpod`/`@Riverpod(keepAlive: true)` providers, and no legacy APIs. `keepAlive` is limited to infrastructure (config, DB, Dio, session, router, gate). Global retry is disabled (`bootstrap.dart:14,21`). Action notifiers check `ref.mounted` after awaits (`sample_providers.dart:43,69`; `sample_demo_entry.dart:30`). The screen watches its action providers for the whole operation, and one-shot snackbars are transition-driven with `ref.listen`.
- **Refresh architecture (§11–§13):** The interceptor depends on `SessionManager`, not an auth repository. Refresh uses a separate Dio with no auth interceptor (`network_providers.dart:33-46`). Login and refresh paths are skipped. There is one shared in-flight refresh per epoch, plus token-changed detection. Each request is retried at most once (`_retryKey`), so there is no recursion. Rejected refreshes (401/403/`invalid_grant`) are distinguished from unavailable ones (timeouts, connection errors, 5xx, malformed responses): a rejection logs out, and unavailability keeps the session offline and returns `NetworkFailure`. Multipart `FormData`/`MultipartFile` bodies are cloned for the retry, and one-shot streams are refused.
- **Logout ordering (§19):** The order is epoch → unauthenticated → cancel → clear access token → delete envelope (serialized behind pending writes) → clear account Drift data in one transaction → clear `user.*`. Device keys survive.
- **Epoch write guard (§15, §37):** Both refresh and create check `isCurrentSession` inside the Drift transaction, at the start and just before commit. The logout-race test uses an API that ignores cancellation, so it proves the guard works on its own (`test/sample/sample_repository_test.dart:129-155`).
- **Cold-start restoration (§14):** restoring → unauthenticated (missing, corrupt or unreadable envelope) / authenticatedOffline (network failure) / authenticatedOnline. The access token is kept in memory only, and the refresh token plus account ID live in one secure envelope.
- **Persistence (§16–§17, §20–§26, §28):** `SharedPreferencesAsync` with `device.`/`user.` prefixes. Drift runs through one provider with `onDispose(close)`. Every table has an `account_id` composite key. Schema v1 and v2 are exported and migration tests are generated. `cache_metadata_entries` distinguishes never-fetched from empty.
- **Android backup (§22–§23):** `backup_rules.xml` and `data_extraction_rules.xml` exclude `sharedpref`, `datastore/` and the SQLite file plus its sidecars, for both cloud backup and device transfer. `app_identity.dart` rewrites the DB filename in both files.
- **Online-first sample (§27–§36, §74–§75):** No network call in provider `build`. The screen triggers `refreshIfStale` after the first frame. Staleness is decided in the repository. `forceRefresh` covers pull-to-refresh. The complete list is replaced in one transaction. View state is derived from rows + metadata + action state, and all five §30 states are covered by `sample_view_state_test.dart`.
- **Errors (§39–§41, §67):** A hand-written sealed `Result` and `AppFailure`. Failures are classified by type and enum, never by `runtimeType` strings. Messages are localized through an exhaustive `switch`. `ProviderException` is unwrapped at the presentation boundary.
- **Logging and redaction (§63):** `RedactedLogInterceptor` logs only the method and status, never headers, URLs or bodies, and is disabled in prod. It is backed by a test.
- **Flavors and developer flags (§50–§51):** dev/staging/prod exist with distinct Android and iOS IDs, and dev is the default flavor. The showcase route is removed at compile time by a `const bool.fromEnvironment` flag, with a prod runtime check as well.
- **Secrets (§53):** None are committed. Config files contain only public `.invalid` hosts. `docs/release.md` states that obfuscation does not protect secrets and says to archive symbols.
- **Localization and accessibility (§56–§57):** gen-l10n output lives in `lib/l10n/generated` (no `flutter_gen`). Plurals, parameters, dates and numbers are all used. Contrast tests run on both themes. Large-text (250%) and short-viewport widget tests are in place. Status is shown with icon + text, and live regions are set on loading and error states.
- **Tooling and CI (§66, §69–§70):** `tool/app_identity.dart` supports preview and apply and is tested. `tool/verify.sh` exists. CI covers generation diff, format, analyze, tests, the Android dev debug APK and the iOS dev no-codesign build on `macos-26`.
- **Tests (§61, Phase 7):** Deterministic `HttpClientAdapter`-based tests cover concurrent 401s → one refresh, a late old-token 401, refresh rejection, refresh network failure, offline cold start, the logout race and the multipart retry.
